# Техническое задание

## 0. Глоссарий

| Термин | Определение |
|---|---|
| LLM | Большая языковая модель, которая преобразует входной текст в структурированный JSON |
| MVP | Минимально жизнеспособный продукт: работает сквозной сценарий, есть проверка качества, журнал и действие |
| Сценарий | Настройка одного бизнес-процесса: поддержка, продажи или документы |
| Эскалация | Передача случая человеку, если модель не уверена, не хватает данных или произошла ошибка |
| Аудит | Журнал, в котором хранятся вход, сырой ответ модели, результат, статус и ошибка |
| Fallback | Безопасный результат для случая invalid/error: задача передаётся оператору |
| JSON-режим | Режим ответа LLM, в котором модель обязана вернуть валидный JSON-объект |
| AITUNNEL | OpenAI-совместимый агрегатор моделей, используемый как LLM-провайдер |
| QC | Quality control, контроль качества: валидация, бизнес-правила и эскалация |

## 2. Цели и назначение ПО

### 2.1 Назначение ПО

ПО принимает входящий текст, отправляет его в LLM, получает строгий JSON, проверяет структуру и бизнес-правила, при необходимости эскалирует случай человеку и сохраняет результат в базе данных.

Определение через функционал:

1. Приём текста через HTTP API или CLI.
2. Выбор одного из трёх сценариев: поддержка, продажи, документы.
3. Извлечение и структурирование данных через LLM.
4. Валидация JSON и обязательных полей.
5. Эскалация при низкой уверенности, нехватке данных или ошибке.
6. Запись в журнал аудита и в таблицу бизнес-результатов.
7. Выдача результата через API и экспорт в CSV/JSONL.
8. Пакетный прогон тестовых кейсов и сбор статистики.

### 2.2 Цели ПО

1. Сократить время ручной обработки входящих обращений, лидов и документов.
2. Снизить количество ошибок за счёт строгой схемы и детерминированных правил.
3. Сделать процесс прозрачным: сохранить вход, результат, статус и причину эскалации.
4. Показать повторяемый инженерный подход: один конвейер, три конфигурации процесса.
5. Подготовить портфолио-кейс с демо, отчётом, защитой и экономическим обоснованием.

#### 3.1.2 Приём входа

Система должна принимать POST /ingest с телом:

```json
{
  "scenario": "support",
  "text": "Текст обращения",
  "source": "api",
  "metadata": {}
}
```

Требования:

1. scenario обязателен и принимает значения support, sales, documents.
2. text обязателен, от 3 до 20 000 символов.
3. source необязателен, по умолчанию api.
4. metadata необязателен, словарь строк.
5. При неверном теле возвращается HTTP 422.
6. При корректном теле возвращается HTTP 200 и бизнес-результат.

#### 3.1.3 Сценарий A. Поддержка

Вход: текст обращения клиента.

Выход: категория billing, delivery, technical, return, complaint или other; резюме; приоритет; следующее действие; поля client_name, contact, order_id, product, issue, desired_outcome; confidence; escalate; missing_fields.

Критичные данные: issue или desired_outcome, а также хотя бы один контакт — client_name или contact.

#### 3.1.4 Сценарий B. Продажи

Вход: текст лида или заявки.

Выход: категория hot, warm, cold или spam; score от 0 до 100; резюме; следующий шаг; поля contact_name, company, contact, need, budget, urgency, source.

Правило согласованности: hot 70-100, warm 40-69, cold 1-39, spam 0. Несовпадение score и категории приводит к эскалации.

Критичные данные: need и хотя бы один контакт — contact или company.

Исключение: чистый спам отклоняется без эскалации.

#### 3.1.5 Сценарий C. Документы

Вход: текст ТЗ, брифа или договора.

Выход: категория tz, brief, contract или other; резюме; следующий шаг; поля customer, project, deadline, budget, scope, acceptance_criteria; черновик КП.

Черновик КП собирается детерминированным шаблоном из извлечённых полей. Модель не придумывает цены и сроки.

Критичные данные: project и scope.

#### 3.1.6 LLM-обработка

1. Провайдер: AITUNNEL, OpenAI-совместимый API.
2. Модель по умолчанию: gpt-4o-mini; в текущей конфигурации допускается deepseek/deepseek-v4.1-flash-1017. Модель задаётся в .env.
3. Температура: 0.2.
4. Ответ: JSON-объект, response_format type=json_object.
5. Максимум токенов ответа: 2500 (reasoning-модели расходуют часть бюджета на рассуждения).
6. Таймаут: 60 секунд.
7. Повторы: две попытки при таймауте, сетевой ошибке, 429 или 5xx.
8. Ключ и модель задаются через .env.
9. Ключ не попадает в логи и репозиторий.
10. Если ответ обрезан по лимиту max_tokens, выполняется повтор с удвоенным лимитом; если ответ снова обрезан, запрос переводится в статус error.

#### 3.1.7 Валидация JSON

1. Ответ должен быть JSON-объектом.
2. Допускается снятие markdown-обёртки и извлечение первого объекта.
3. Обязательные поля: summary, priority, next_action, fields, confidence, escalate.
4. Для сценария A обязателен category из перечисления.
5. Для сценария B обязательны category и score 0-100.
6. Для сценария C обязателен category из перечисления.
7. Enum-поля нормализуются по регистру.
8. Пустые fields приводятся к пустому объекту.
9. Неизвестные поля игнорируются.
10. Ошибка валидации переводит запрос в статус invalid.

#### 3.1.8 Эскалация

1. confidence=low принудительно включает эскалацию.
2. Отсутствие критичных полей включает эскалацию.
3. escalate=true от модели уважается.
4. Несогласованность score и категории включает эскалацию.
5. Пустые summary или next_action включают эскалацию.
6. Невалидный JSON переводит запрос в invalid и возвращает fallback.
7. Ошибка LLM переводит запрос в error и возвращает fallback.
8. При эскалации сохраняются вход, результат и причина.
9. Клиент всегда получает бизнес-результат.

#### 3.1.9 Журнал аудита

Таблица processing_log должна хранить:

1. id запроса;
2. сценарий;
3. источник;
4. входной текст;
5. SHA-256 хеш входа;
6. статус;
7. результат JSON;
8. сырой ответ LLM;
9. ошибку;
10. модель;
11. температуру;
12. latency;
13. usage;
14. metadata;
15. дату и время.

#### 3.1.10 Действие на выходе

1. Запись бизнес-результата в business_results.
2. Поля: id, log_id, сценарий, статус, категория, приоритет, резюме, следующее действие, поля, confidence, escalate, причина, missing_fields, score, result_json, дата.
3. Экспорт результатов в CSV.
4. Экспорт журнала в JSONL.
5. Запись выполняется в одной транзакции с журналом.

#### 3.1.11 API чтения

1. GET /results — список с фильтрами scenario и status, limit и offset.
2. GET /results/{request_id} — результат по ID.
3. GET /audit/{request_id} — журнал; сырой ответ только при include_raw=true или DEBUG=true.
4. GET /stats — статистика.
5. GET /health — статус приложения, БД и LLM-конфига.
6. GET /export/results.csv — CSV.
7. GET /export/audit.jsonl — JSONL.
8. GET /scenarios — список сценариев и схем.

#### 3.1.12 CLI и тесты

1. CLI ingest — один вход из текста или файла.
2. CLI batch — пакетный прогон JSONL.
3. CLI stats — статистика по базе.
4. Mock-тесты не обращаются к реальному LLM.
5. Live-прогон использует реальный ключ AITUNNEL.
6. Пакетный прогон сохраняет JSON и CSV с результатами.
7. Прогон поддерживает строгий режим проверки ожидаемых статусов.

#### 3.1.13 README и документация

1. README написан без markdown-разметки.
2. README содержит установку, настройку, запуск, API, тесты и ограничения.
3. Скрипт check_readme.py проверяет отсутствие markdown.
4. README обновляется после каждого изменения проекта.
5. Документация включает ТЗ, отчёт, демо, защиту и мини-экономику.

### 3.2 Нефункциональные требования

#### 3.2.1 Требования к надежности

1. Режим функционирования: по запросу, один экземпляр приложения.
2. Целевая доступность демо: не ниже 99 процентов в период защиты.
3. Время простоя при обновлении: не более 5 минут на учебном стенде.
4. Время восстановления после сбоя: не более 15 минут при наличии копии SQLite.
5. Возможность копирования БД: файл SQLite и WAL-файлы.
6. Повторные попытки LLM: две попытки при временных ошибках.
7. Fallback при ошибке: бизнес-результат с передачей оператору.
8. Мониторинг: GET /health и журнал обработки.
9. Тестирование: unit-тесты, API-тесты, live-прогон 30 кейсов.

#### 3.2.2 Требования к масштабируемости

1. MVP работает на одном экземпляре FastAPI и SQLite.
2. Горизонтальное масштабирование в MVP не требуется.
3. Архитектура должна позволять заменить SQLite на PostgreSQL без изменения бизнес-логики.
4. В v2 предусмотреть очередь задач и несколько воркеров.
5. Целевая нагрузка MVP: до 500 запросов в сутки.
6. Целевая нагрузка v2: до 1000 одновременных запросов при времени отклика не более 2 секунд без учёта LLM.
7. Балансировка нагрузки в v2: NGINX или HAProxy.

#### 3.2.3 Требования к производительности

1. Время отклика API с учётом LLM: типично 2-15 секунд.
2. Таймаут LLM: 60 секунд.
3. Время отклика чтения из SQLite: не более 1 секунды.
4. Пакетный прогон 30 кейсов: не более 15 минут последовательно.
5. Пропускная способность MVP: не менее 10 запросов в минуту на одном worker.
6. Одновременные пользователи MVP: до 5 без деградации.
7. Целевые показатели v2: 1000 одновременных запросов, p95 без LLM не более 2 секунд.

1. Уровень автоматизации: целевой ориентир — 70 процентов кейсов без участия человека; фактический уровень фиксируется в отчёте по live-прогону.
2. Темы обработки: поддержка, продажи, документы.
3. Объём тестового прогона: 30 кейсов, по 10 на сценарий.
4. Объём обрабатываемых данных: до 20 000 символов на один вход.
5. Действие на выходе: запись в SQLite и экспорт.
6. Язык обработки: русский.

#### 3.2.5 Показатели качества и требования к ним

1. Доля валидных JSON на тестовом наборе: не менее 98 процентов.
2. Доля корректных бизнес-результатов на явных кейсах: не менее 85 процентов.
