# Отчёт по практике

## 1. Выбранный сценарий и почему

Основной сценарий для отчёта и защиты — A, поддержка клиентов. Это самый частый и понятный процесс: входящие обращения легко измерить в минутах, у него очевидные метрики (время обработки, доля эскалаций, ошибки), а результат важен бизнесу.

Сценарии B и C реализованы как дополнительные конфигурации того же конвейера. Это осознанное расширение: задание предлагает выбрать один процесс, но один и тот же код с разными схемами и промптами показывает, что решение переиспользуемо. В отчёте фокус на A; B и C подтверждают универсальность архитектуры.

## 2. Проблема, контекст, ограничения

### Проблема

Малый или средний бизнес получает входящие сообщения, лиды и документы в разных каналах. Сотрудники вручную читают текст, выделяют ключевые данные, выбирают действие и переносят информацию в таблицы или CRM. Из-за этого:

- теряется время на рутину;
- данные приходят в разном формате;
- ошибки и пропуски не видны;
- нет прозрачного журнала, кто и что обработал;
- сложно понять, сколько стоит обработка одного обращения.

### Контекст

Клиент — небольшой бизнес с потоком входящих до 500 единиц в сутки. Входные данные — текст на русском языке. Выход — структурированная карточка и понятное следующее действие.

### Ограничения MVP

- один вход: HTTP API, дополнительно CLI для тестов;
- одно действие: запись в SQLite и экспорт;
- максимум две интеграции: AITUNNEL и SQLite;
- без CRM, почты, авторизации и мультитенантности;
- один экземпляр приложения, SQLite;
- модель может ошибаться, поэтому обязательны валидация, эскалация и аудит.

## 3. Архитектура процесса

```text
Клиент (Swagger, curl, CLI)
        |
        v
FastAPI POST /ingest
        |
        v
Реестр сценариев: support / sales / documents
        |
        v
Prompt builder: системный промпт + схема + input в тегах
        |
        v
AITUNNEL /chat/completions
model из .env, temperature=0.2, response_format=json_object
        |
        v
JSON parse -> Pydantic validation -> QC / эскалация
        |
        v
SQLite: processing_log (аудит) + business_results (действие)
        |
        v
Ответ: status + бизнес-результат + meta
```

Компоненты:

- app/main.py — FastAPI, маршруты, lifespan;
- app/config.py — настройки из .env;
- app/llm.py — клиент AITUNNEL, повторы, usage;
- app/schemas.py — Pydantic-модели;
- app/scenarios — схемы, промпты и правила трёх сценариев;
- app/qc.py — разбор JSON, валидация, эскалация, fallback;
- app/db.py — SQLite, журнал, результаты, статистика;
- app/service.py — оркестрация конвейера;
- app/cli.py — одиночная и пакетная обработка.

## 4. Формат структурированного JSON

Общая схема:

```json
{
  "category": "delivery",
  "summary": "Клиент оплатил заказ №12345, но доставка не пришла.",
  "priority": "high",
  "next_action": "Проверить статус заказа №12345 и связаться с клиентом.",
  "fields": {
    "client_name": "Анна",
    "contact": "+7 900 123-45-67",
    "order_id": "12345",
    "product": null,
    "issue": "заказ не доставлен",
    "desired_outcome": "получить заказ"
  },
  "confidence": "high",
  "escalate": false,
  "escalate_reason": null,
  "missing_fields": ["product"]
}
```

Для продаж добавляется score 0-100 и категория hot/warm/cold/spam.
Для документов добавляется draft_kp, который собирается сервисом, а не моделью.

Почему JSON-режим, а не json_schema: json_schema поддерживается не всеми моделями AITUNNEL. Мы требуем JSON в промпте и проверяем его на сервере через Pydantic. Это надёжнее, потому что качество контролирует код, а не обещание модели.

## 5. Контроль качества

После ответа модели применяются детерминированные правила:

| Правило | Условие | Действие |
|---|---|---|
| R1 | Ошибка LLM после повторов | fallback, статус error |
| R2 | Невалидный JSON | fallback, статус invalid |
| R3 | Ошибка Pydantic | fallback, статус invalid |
| R4 | confidence=low | эскалация |
| R5 | Нет критичных полей | эскалация |
| R6 | Модель поставила escalate=true | эскалация |
| R7 | Score не совпадает с категорией | эскалация |
| R8 | Пустые summary или next_action | эскалация |
| R9 | Prompt injection | эскалация |
| R10 | Ответ обрезан по max_tokens | повтор с удвоенным лимитом; если снова обрезан — error |
| R11 | Все проверки пройдены | processed |

Для поддержки критична пара: issue или desired_outcome, а также хотя бы один контакт. Это позволяет обрабатывать общие вопросы о доставке без эскалации, но не терять обращения без сути и без связи.

Статусы: processed, escalated, invalid, error. При любом статусе клиент получает бизнес-результат. Для invalid и error это fallback: «Передать оператору для ручной обработки».

Отдельное правило для продаж: чистый спам отклоняется без эскалации, потому что у него может не быть контакта и компании. Это снижает лишнюю нагрузку на менеджеров.

## 6. Журнал обработки и аудит

Таблица processing_log хранит:

- id запроса;
- сценарий и источник;
- входной текст и SHA-256 хеш;
- статус;
- результат JSON;
- сырой ответ LLM;
- ошибку;
- модель и температуру;
- latency;
- usage и стоимость;
- metadata;
- дату и время.

Таблица business_results хранит бизнес-результат: категорию, приоритет, резюме, следующее действие, поля, confidence, признак эскалации, score и полный JSON.

Сырой ответ доступен через GET /audit/{request_id} при include_raw=true или при DEBUG=true. Это позволяет разбирать инциденты, не показывая лишние данные обычному клиенту.

## 7. Действие на выходе

Действие — запись в SQLite. Это соответствует ограничению «одно действие» и даёт сразу два полезных эффекта:

1. бизнес-результат можно читать через API;
2. журнал можно выгрузить в CSV/JSONL и использовать в отчёте.

Экспорт:

- GET /export/results.csv — результаты;
- GET /export/audit.jsonl — журнал.

В v2 действие можно заменить на отправку в CRM или письмо, не меняя слой LLM и QC.

## 8. Мини-экономика

Допущения для расчёта:

- ручная обработка одного кейса — 6 минут;
- проверка автоматического кейса — 0.5 минуты;
- ручная обработка эскалированного кейса — 5 минут;
- 30 тестовых кейсов;
- 20 кейсов обработаны автоматически, 10 эскалированы.

Расчёт:

- вручную: 30 × 6 = 180 минут;
- с автоматизацией: 20 × 0.5 + 10 × 5 = 10 + 50 = 60 минут;
- экономия: 120 минут, или 66.7 процента;
- стоимость LLM на 30 кейсов: 2.04 рубля;
- стоимость 100 обработок: 6.8 рубля, основная ценность — не цена токенов, а сокращение ручных минут и прозрачность.

Вывод: даже при 33.3 процентах эскалаций автоматизация экономит две трети ручного времени. Чем стабильнее входные данные, тем выше доля автоматической обработки.

## Приложение. Результаты тестов

Live-прогон выполнен на модели deepseek/deepseek-v4.1-flash-1017:

- всего кейсов: 30;
- валидных бизнес-результатов: 30;
- invalid: 0;
- error: 0;
- обработано автоматически: 20;
- эскалировано: 10;
- уровень автоматизации: 66.7 процента;
- средняя задержка: 3397 мс;
- стоимость прогона: 2.04 рубля;
- совпадение с ожидаемым статусом: 30/30.

Первая итерация live-прогона дала 27 валидных результатов и 3 invalid. Причина — обрезка JSON по лимиту max_tokens=800: reasoning-модель расходовала 594-676 токенов на рассуждения, и на видимый JSON оставалось слишком мало. Исправление: max_tokens увеличен до 2500, добавлен повтор с удвоением лимита при finish_reason=length. Вторая итерация дала 30/30 валидных результатов.

Два кейса проверяют границы эскалации. support_06 — общий вопрос о доставке: он должен обрабатываться, если заполнен desired_outcome и есть контакт. support_10 — срочная жалоба с полными данными: допустимы и processed, и escalated, поэтому для него не фиксируется единственный ожидаемый статус. Это не подгонка результата, а признание бизнес-неоднозначности.

Mock-тесты: 69 passed. Они проверяют схемы, QC, API, LLM-клиент, pricing, базу, экспорт и формат README.
