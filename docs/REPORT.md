# Отчёт по выпускному проекту

## 1. Название проекта

**Call-Pilot — AI-постобработка и контроль качества звонков для колл-центров.**

Формат: веб-панель + API + SQLite + языковая модель + контроль качества + аудит.

Проект можно отнести к варианту «Персональный помощник: от текста к действию»:
вход — транскрипт звонка, выход — структурированная карточка, QA-решение
и конкретное следующее действие для оператора или менеджера.

## 2. Ценность: для кого и зачем

Для руководителя колл-центра и службы качества:

- QA слушает 2–5% звонков, остальное — слепая зона;
- оператор тратит 3–4 минуты на карточку и резюме;
- жалобы, возвраты и ложные обещания всплывают постфактум;
- нет единой картины, какие ошибки повторяются из звонка в звонок.

Call-Pilot проверяет 100% звонков, готовит карточку и показывает
только исключения. AI не пишет в CRM без подтверждения человека:
сначала оператор проверяет карточку, затем CRM получает финальную версию.

Ценность:

1. Меньше рутины на постобработку.
2. Полное покрытие QA вместо выборочного.
3. Прозрачный аудит: что предложила модель и что изменил человек.
4. Внедрение без замены операторов и без риска для клиентской базы.

## 3. Контекст и ограничения

- Публичное демо работает на 6 синтетических звонках, без реальных ПДн.
- Один контур, SQLite для демо; production может быть на PostgreSQL.
- Нет реальной телефонии и production-нагрузки — это следующий шаг пилота.
- AI не заменяет оператора: решение принимает человек.
- Реальные записи требуют согласия, маскирования и настройки хранения.

## 4. Три пользовательских сценария

### Сценарий 1. Оператор после звонка

1. Звонок появляется в очереди.
2. AI расшифровывает его и заполняет карточку: интент, резюме,
   следующий шаг, поля CRM.
3. Оператор открывает карточку, слушает аудио с таймкодами,
   проверяет поля и подтверждает.
4. В CRM уходит финальная версия с аудитом.

### Сценарий 2. QA-менеджер разбирает исключения

1. Менеджер открывает `/dashboard` и видит очередь `need_review`.
2. Система показывает причину: critical-нарушение, низкий QA-score,
   негативный клиент или низкая уверенность.
3. Менеджер слушает фрагмент, читает цитату и таймкод,
   подтверждает или отклоняет карточку.
4. Решение и правки фиксируются в `audit_runs`.

### Сценарий 3. Руководитель смотрит картину

1. Открывает `/qa`: покрытие QA, auto-pass, топ нарушений, SLA.
2. Открывает `/audit`: кто, что и когда сделал.
3. Выгружает `/export/results.csv` и `/export/audit.jsonl`.
4. Считает экономику на своём объёме звонков.

## 5. Точки доступа API

### 4.1. Создание звонка

`POST /api/v1/calls`

Принимает `title`, `transcript`, `client`, `operator`, `external_id`.
Создаёт сущность в базе и возвращает `call_id`, `need_review=false`,
`status=new`.

### 4.2. Чтение списка

`GET /api/v1/calls`

Фильтры: `status`, `source`, `need_review`, `limit`, `offset`.
Возвращает список звонков с `qa_score`, `need_review`,
`review_reason` и статусом.

### 4.3. AI-обработка

`POST /api/v1/calls/{call_id}/process`

Вызывает языковую модель, валидирует JSON по схеме и возвращает:

- `result` — карточка и QA-чек-лист;
- `status` — processed или escalated;
- `need_review` — нужна ли ручная проверка;
- `review_reason` — почему;
- `meta` — модель, температура, latency, usage.

Дополнительно:

- `GET /api/v1/calls/{call_id}` — карточка и транскрипт;
- `GET /api/v1/audit` — журнал действий;
- `GET /export/results.csv` — результаты;
- `GET /export/audit.jsonl` — аудит.

## 6. Схема данных

SQLite: `call-center/data/call_center.db`.

### Таблица `demo_calls`

Хранит звонок: `id`, `title`, `client`, `operator`, `transcript_json`,
`audio_file`, `created_at`, `source`, `external_id`, `duration_ms`,
`audio_mime`, `audio_deleted_at`.

### Таблица `call_reviews`

Хранит решение по звонку: `call_id`, `request_id`, `status`,
`reviewer`, `final_json`, `changes_json`, `reason`, `need_review`,
`review_reason`, `updated_at`.

### Таблица `audit_runs`

Хранит каждое действие: `id`, `call_id`, `action`, `input_json`,
`output_json`, `status`, `error`, `duration_ms`, `created_at`.

### Таблица `leads`

Заявки с лендинга: `id`, `name`, `company`, `contact`, `volume`,
`phone_system`, `comment`, `consent`, `created_at`.

Движок дополнительно ведёт `processing_log` и `business_results`
для хранения сырого ответа модели и бизнес-результата.

## 7. AI-операция

Модель: AITUNNEL, текущая конфигурация `deepseek/deepseek-v4.1-flash-1017`.
Температура: `0.2`. Режим: `json_object`, без markdown и пояснений.
Сервер валидирует ответ через Pydantic-модель `CallResult`.

Схема ответа (сокращённо):

```json
{
  "call_type": "inbound",
  "intent": "refund",
  "summary": "Клиент требует возврат за бракованный товар.",
  "resolution": "Оператор обещал возврат сегодня.",
  "next_action": "Передать руководителю и проверить регламент.",
  "priority": "high",
  "fields": {
    "client_name": "Мария",
    "phone": null,
    "order_id": null,
    "product": null,
    "amount": null,
    "address": null
  },
  "sentiment": "negative",
  "qa_score": 0,
  "qa_findings": [
    {
      "criterion_id": "accuracy",
      "criterion": "Достоверность информации",
      "status": "fail",
      "severity": "critical",
      "evidence": "Я гарантирую, что деньги вернутся сегодня",
      "segment_id": "s3",
      "comment": "Ложное обещание срока возврата."
    }
  ],
  "confidence": "high",
  "escalate": true,
  "escalate_reason": "Критичное нарушение: ложная гарантия возврата.",
  "missing_fields": ["phone", "order_id"]
}
```

### Когда нужна ручная проверка

`need_review=true` выставляется, если:

1. Есть critical или high нарушение.
2. QA-score ниже 85.
3. Клиент негативен, а тема — жалоба или возврат.
4. Модель вернула `confidence=low` или `escalate=true`.
5. В ответе нет критичных полей.
6. В транскрипте обнаружена попытка prompt injection.

Причина сохраняется в `review_reason` и видна в API, карточке звонка
и журнале аудита.

## 8. Память и контекст

Долговременной памяти нет: каждый звонок обрабатывается отдельно.
Контекст ограничен транскриптом одного звонка. PII-данные маскируются
до отправки в модель и хранятся в отдельном vault с TTL. Это осознанное
ограничение: оно снижает риск утечки и делает поведение предсказуемым.

## 9. Контроль качества

### На входе

- проверка длины и обязательности транскрипта;
- маскирование телефонов, имён, email и адресов;
- ограничение размера аудио и загрузки;
- защита от SSRF при загрузке по URL.

### На выходе

- парсинг JSON;
- валидация Pydantic по схеме `CallResult`;
- проверка типов, перечислений и диапазона QA-score;
- детерминированный пересчёт QA-score по severity;
- critical/high нарушения не могут быть занижены моделью;
- auto-pass только при score ≥ 85 и отсутствии critical/high;
- fallback и `need_review=true` при ошибке модели.

### Аудит

Каждое действие пишется в `audit_runs`: создание, AI-обработка,
подтверждение, отклонение, загрузка аудио. Видны вход, выход, статус,
ошибка и длительность.

## 11. Мини-экономика

Допущения:

- 1 000 звонков в месяц;
- 3 минуты на ручную карточку;
- 215 ₽/час стоимости оператора;
- 80% рутины снимает AI;
- стоимость AI-разбора — около 0,33 ₽ за звонок.

Расчёт:

| Показатель | Значение |
|---|---|
| Часов рутины в месяц | 50 ч |
| Сэкономленные часы | 40 ч |
| Экономия в месяц | 8 600 ₽ |
| AI-разбор 1 000 звонков | 330 ₽ |
| Чистая экономия в месяц | 8 270 ₽ |
| Экономия на один звонок | 8,6 ₽ |
| Экономия за год | 99 240 ₽ |

На 100 операций:

- вручную: 100 × 3 = 300 минут = 5 часов;
- с AI: 20% ручной проверки = 1 час;
- экономия: 4 часа = 860 ₽;
- AI-разбор: 33 ₽;
- чистая экономия: 827 ₽.

При 10 000 звонков в месяц экономия масштабируется примерно до 86 000 ₽/мес.
Точные цифры зависят от качества записей, доли auto-pass и стоимости часа.

## 12. Риски и снижение

1. **Модель выдумывает факты.** Промпт запрещает добавлять данные,
   которых нет в транскрипте; обязательны `missing_fields`, низкая
   температура и ручная проверка спорных случаев.
2. **Невалидный JSON.** Pydantic-валидация, повтор при обрезке,
   fallback и `need_review=true`.
3. **Утечка ПДн.** Синтетика в публичном демо, маскирование до LLM,
   PII-vault, шифрование аудио, запрет реальных записей на демо-стенде.
4. **Ошибка интеграции с CRM.** Durable-outbox, повторные попытки,
   `ORIGIN_ID` / Call-Pilot ID для ручной сверки.
5. **Плохое качество аудио.** Confidence, ручная проверка, локальный STT
   и пилот на реальных записях до production.
6. **Недоверие операторов.** HITL, видимые правки, аудит и пилот
   на ограниченной выборке.
7. **152-ФЗ.** On-prem, согласие на запись, сроки хранения и поручение
   на обработку ПДн.

## 16. Сложности и решения

1. **Обрезка JSON у reasoning-модели.** Увеличили `max_tokens` до 2500
   и добавили повтор с удвоенным лимитом при `finish_reason=length`.
2. **Один говорящий в тестовом транскрипте.** Добавили разбор реплик
   по строкам `Оператор:` / `Клиент:` и сохраняем сегменты с ролями.
3. **PII в звонках.** Сделали маскирование, vault и синтетическое демо.
4. **Недоверие к AI.** Ввели HITL: AI готовит черновик, человек
   подтверждает, CRM получает только финальную версию.
5. **Долгая обработка.** Вынесли в очередь и outbox, добавили
   идемпотентность по `external_id` для аудио.
